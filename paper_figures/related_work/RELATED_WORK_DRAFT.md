\section{Related Work}

\paragraph{Validating speculation defenses.}
Most leakage testing samples programs at random. Revizor~\cite{revizor} and its follow-ups~\cite{oleksenko2023hideseekspectresefficient,hofmann2023speculationatfault} test commercial CPUs against speculation contracts, and AMuLeT~\cite{amulet} carries this relational testing to gem5 prototypes of secure-speculation defenses (Sec.~\ref{sec:bg-litmus}).
% DECIDE(Anna): the audit note proposes moving the single AMuLeT description into this section; if you do that, expand the AMuLeT clause above and delete the Sec.~\ref{sec:bg-litmus} pointer.
Pre-silicon fuzzers search RTL for transient-execution bugs through differential execution~\cite{hur2022specdoctor,xu2025dejavuzz}, gadget-driven simulation~\cite{ghaniyoun2021introspectre}, information-flow tracking~\cite{rostami2024specure,defaveritron2025phantomtrails}, or contract-guided coverage~\cite{geier2025coverage}. SpecCheck~\cite{mckevitt2023speccheck}, the closest gem5-based tool, monitors simulation for a generic transient-attack pattern described as a register-based state machine, and Scam-V~\cite{nemati2020scamv} generates programs to validate an abstract side-channel model against hardware. Formal tools instead prove secure speculation for RTL designs~\cite{fadiheh2019upec,contractshadow,leave,dong2026interplay}, which most defense proposals do not yet have. \toolname{} differs from the testing tools in two ways: it checks each simulated defense against that defense's own guarantee rather than a generic attack or a sequential contract, and it enumerates only programs that contain a leak the defense claims to block rather than sampling programs at random.

\paragraph{Leakage contracts and security definitions.}
Formal definitions of secure speculation began with information-flow properties over speculative executions~\cite{cheang2019formal} and speculative non-interference~\cite{guarnieri2020spectector}, which Guarnieri et al.\ generalized into hardware--software contracts with an observation clause and an execution clause~\cite{guarnieri2021contracts}. The OISA proposal~\cite{yu2019oisa} introduced the split into safe and unsafe operands that later defenses call transmitters. On the software side, these definitions underpin verified compilers and analyses (surveyed in~\cite{cauligi2022sok}). On the hardware side, recent work verifies contracts against RTL~\cite{leave}, synthesizes them~\cite{mohr2024synthesizing,synthlc,rtl2upath}, and proves which instructions are safe for unbounded executions~\cite{dinesh2024conjunct,dinesh2025hhoudini}. Leakage containment models~\cite{lcms} recast contracts axiomatically, the formalism \toolname{} builds on. \toolname{}'s leakage function plays the role of the observation clause and its speculation contract that of the execution clause; its protection set has no counterpart in a contract. Unlike this work, \toolname{} does not prove or synthesize a contract but uses a defense's stated one generatively, to enumerate the tests a correct implementation must not leak on.
% DECIDE(Anna): the three-component-to-two-clause mapping should appear once; if it goes into Sec.~\ref{sec:bg-defenses}, cut the "plays the role of" sentence to a back-reference.

\paragraph{Axiomatic models and litmus-test synthesis.}
\toolname{}'s method comes from memory-consistency-model verification (Sec.~\ref{sec:bg-axiomatic}). Alloy~\cite{jackson2002alloy}, backed by the Kodkod model finder~\cite{torlak2007kodkod}, has been used to compare memory models through distinguishing tests~\cite{memalloy} and to synthesize complete suites of minimal litmus tests~\cite{lustig,hossain2020transform}, and RTLCheck~\cite{manerkar2017rtlcheck} checks such tests against RTL. CheckMate~\cite{checkmate} brought this approach to security: it synthesizes exploit litmus tests from happens-before models of an undefended pipeline, and it found new attack variants~\cite{trippel2018meltdownprime}. \toolname{} applies minimal-test enumeration to speculation \emph{defenses}. Its model encodes the defense's guarantee, so each test contains a leak the defense claims to block, and the defense's gem5 implementation, not the model, is the object under test.
% DECIDE(Anna): "the implementation, not the model, is the object under test" is the CheckMate contrast as RW3 framed it; confirm it is the claim you want.

\paragraph{Execution models of speculation.}
Several works give speculation a formal semantics. Program-level models capture speculative evaluation with pomsets~\cite{disselkoen2019code} or abstract semantics~\cite{colvin2020abstractsemantics}, and Cats vs.\ Spectre~\cite{ponce2022cats} extends axiomatic memory models with speculative relations to find gadgets in software. Closer to hardware, InSpectre~\cite{guanciale2020inspectre} gives an operational out-of-order semantics and analyzes countermeasures, Pensieve~\cite{pensieve} model-checks early-stage defense designs for speculative non-interference, and RTL2M$\mu$PATH~\cite{rtl2upath} synthesizes execution-path models bottom-up from RTL. Defenses such as STT carry pen-and-paper proofs over an abstract machine~\cite{yu2019sttformal}. \toolname{}'s model is not a full execution semantics but an abstract snapshot of microarchitectural state (resolved and committed flags, the protection set, and transmitters), and instead of proving that model secure, \toolname{} uses it to check whether an implementation realizes it.

\paragraph{Spectre hardware defenses and their flaws.}
Hardware defenses fall into a few classes~\cite{hu2021sok} (Sec.~\ref{sec:intro}): delay and taint-tracking schemes such as NDA, STT, SPT and ReCon~\cite{nda,yu2019stt,spt,recon}; invisible-speculation schemes such as InvisiSpec and SpecLFB~\cite{yan2018invisispec,cheng2024speclfb}; undo schemes such as CleanupSpec~\cite{saileshwar2019cleanupspec}; and data-oblivious execution~\cite{sdo}. Many were later broken at the design level, by speculative interference~\cite{behnia2021interference}, by rollback timing in CleanupSpec~\cite{li2022unxpec}, by the speculative-store and memory-ordering channels DOLMA identified in STT~\cite{loughlin2021dolma}, and most recently by reservation-station contention from CMOV-selected \texttt{REP} string micro-ops, which bypasses STT and DOLMA in gem5~\cite{cheng2026contention}.

## Intro: where Pensieve goes (2026-11-11, proposed; Anna pastes)

Source: `~/Documents/quail/sources/papers/yang-2023-pensieve.pdf`. Pensieve hand-writes each defense as an abstract µarch model in Rosette. The model is built from modules, each split into a functionality part and a timing part, and the timing parts use uninterpreted functions, so one model covers every latency choice (p2). It defines security as speculative non-interference: two secrets that look the same on an ISA machine must also look the same on the out-of-order machine (p4 §3). Its checker runs the model symbolically for a bounded number of cycles and asks an SMT solver for a program and initial state that break that property (p8 §5.2). The bound is 9 steps (p12 §8). It tested DoM, InvisiSpec, SafeSpec, GhostLoads, MuonTrap and GhostMinion, and found a new interference variant that breaks GhostMinion (p2). It also reports that the open-source gem5 GhostMinion does not implement leapfrogging at all (p10). It never runs the gem5 prototype, and it checks a generic property, not the defense's own guarantee. Extending it to STT and NDA needs a different property, and it cannot evaluate CleanupSpec (p12 §8).

Proposed `intro.tex:14`, Pensieve added as the third item: Existing validation either tests fabricated CPUs against generic speculation contracts~\cite{revizor,oleksenko2023hideseekspectresefficient}, verifies or fuzzes RTL designs~\cite{fadiheh2023exhaustive,contractshadow,rtl2upath,hur2022specdoctor,ghaniyoun2021introspectre}, model-checks hand-written models of early-stage designs against speculative non-interference~\cite{pensieve}, or fuzzes simulator prototypes against a sequential baseline~\cite{amulet}; none checks a prototype against the defense's own security guarantee.

Optional `intro.tex:12` (Pensieve is a principled method at this design stage, so this sentence is too strong as written): There exists no principled way to validate a defense's simulator prototype against its security guarantee, which is necessary to do fast high-level iteration.

Optional motivating sentence for the prototype-bugs paragraph: Pensieve's authors found that the open-source gem5 GhostMinion does not implement leapfrogging, which leaves it open to the speculative interference attacks the defense was built to stop~\cite{pensieve}.
