### 1. Reviewer-level assessment

**The job.** §3 has to define the paper's first contribution, the defense specification language: a precise, formal object that is new relative to SynthLC, Protean and LCMs, expressive enough to state every defense the paper tests, and exactly what the synthesizer enumerates. Today it defines the three clauses informally, gets the polarity of its central predicate backwards in its first sentence, specifies one defense (incorrectly), and never says what it borrowed or what is new.

**Weaknesses (as a PC reviewer would write them).**

- W1. "The central object, the leakage predicate, is defined twice with opposite polarity: it 'holds when the defense forbids that execution' (§3 opening and §1), yet a forbidden execution 'violates' it (the box in §3.2, and §5). It is never stated formally, although the paper calls the specification formal and the language a contribution." (model.tex:9 vs :48; intro.tex:216; pipeline.tex:114.)
- W2. "The only worked example is wrong. §3.3 gives STT's protection set as all memory with an identity update; with the box's dataflow rule, a value loaded by a committed, non-speculative load that feeds a speculative load's address would count as a violation, which STT allows. The paper's own model protects only the memory read by speculative loads (`STT_6_u_lpP.als:413`), and Fig. 1 gives a third version ('unaccessed memory'); Fig. 1 also writes the leakage contract as 'CT with conditions' and the execution contract as 'SpectreCtrl', neither of which §3 uses."
- W3. "§1 claims six defenses are specified in this language and points to §3.3, which specifies one. I cannot judge expressiveness. From §5 I infer that InvisiSpec, CleanupSpec and SpecLFB share one specification and differ only in a 'transmission criterion' that is not part of the language; if so, the language cannot tell three of the six defenses apart. Every evaluated specification also uses the same execution contract, so the clause's value is not shown."
- W4. "What is new is unclear. The leakage contract is SynthLC's, the execution contract is Protean's speculation model, the protection set is Protean's ProtSet, the graph is an LCM-style candidate execution, and rf∪ddi chains are herd's register dependencies (dd-reg = rf-reg ∪ iico). §3 credits none of these, gives no syntax for the 'language', and the abstract's claim that it formalizes 'how a defense's hardware support enforces its guarantee' is not what §3 delivers: it says what is protected and when, not how it is enforced (Protean §III-B separates the two)."
- W5. "Claims about the vocabulary are not checked. §3.1 says it is 'as small as we can' make it, yet Table 1 contains an instruction kind (Other_x) that no evaluated specification uses (the paper's own later caption says so). §3.1's prose and Table 1 define the same items twice, and §3.2 redefines 'transmitter' and 'speculation primitive' differently from §2.1."
- W6. "§3 opens by saying the specification is 'the only defense-specific input to the synthesizer and the executor', but §5.2 says the Inspector uses per-defense transmission criteria written from each paper, and the footprint defenses run on shrunk caches. One of these statements is false."

**Questions for the rebuttal.**

- Q1. Does a forbidden execution satisfy or violate the leakage predicate?
- Q2. Which STT protection set did you evaluate: all memory (Protean §III-C), memory minus locations read non-speculatively (`STT_6.als:329-332`), or the data of speculative loads (`STT_6_u_lpP.als:413`)? Do the results depend on it?
- Q3. Every evaluated specification has the same execution contract. What does the clause buy, and did any reported run use a different one (store bypass, Futuristic)?
- Q4. How do InvisiSpec, CleanupSpec and SpecLFB differ in your language?
- Q5. Why is the leakage predicate the counterpart of an MCM consistency predicate rather than of LCM's confidentiality predicate, which "rule[s] out illegal instantiations of comx according to a specific hardware implementation" (LCM §3.2.2, p.5)?
- Q6. How do you check that a hand-written specification matches its paper?
- Q7. SynthLC says STT and SPT "have the same fine-grained leakage contract" (RTL2MµPATH §II-B, p.4), and §2.2 quotes this, yet your SPT leakage contract adds (store, address) (`SPT_6_oneLP_v2.als:378`). Why?
- Q8. Is the protection set a set of architectural state elements (Protean's definition) or of operand instances (every evaluated model types it as `Operand`)?
- Q9. Why does the shared vocabulary split branches and ALU ops into transmitting (`_x`) and non-transmitting (`_n`) kinds, when the leakage contract is the clause that says which instructions transmit?
- Q10. What attacker does the predicate assume? (§5.2 says "the attacker model is orthogonal to the specification"; that sentence belongs in §3.)

```latex
Each clause adapts a concept from prior work (\S~\ref{sec:bg-contracts}) to one execution graph. \textbf{Leakage contract ($\mathit{LC}$):} the (transmitter, unsafe operand) pairs the defense treats as leaking, in SynthLC's form, each with a \emph{transmission criterion}: the event that counts as that transmission, e.g., a load obtaining its data. \textbf{Execution contract ($\mathit{EC}$):} when an instruction is speculative, i.e., possibly transient, stated over the speculation primitives the defense considers (\S~\ref{sec:bg-defenses}), as Protean's speculation models do. \textbf{Protection set ($\mathit{PS}$):} the data, in memory or registers, that the defense promises to keep from leaking transiently (Protean's ProtSet), with an \emph{update rule} that says how protection propagates: how each instruction, in spo order, adds data to the set or removes it.
```
