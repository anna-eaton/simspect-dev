## Layout and entry points

`Makefile` (the one place for machine paths: `WORK`, `GEM5_ROOT`, `AMULET_REPO`, `AMULET_PY`, `CPUS`, `JOBS`) drives `simspect.py` (the one pipeline script). Run configs under `runconfigs/` carry `@WORK@` / `@GEM5@` placeholders that `simspect.py` renders into `$WORK/configs/`, so nothing else needs editing. Every Python process runs with `PYTHONDONTWRITEBYTECODE=1`; Java is `JAVA`/`JAVAC`. Targets: `setup` (fetch Alloy 6.2.0 jar by URL + sha256, compile the two Java enumerators), `gem5` (`gem5-hits`, `gem5-eval`: scons commands copied from the build scripts in `gem5-hooks/`; `scons-check` fails clearly when SCons is missing), `corpus` (main corpus), `corpus-extra`, `corpus-stt`, `corpus-recon`, `hits`, `classify`, `rounds`, `pool`, `timing`, `amulet-fetch`, `amulet-hits`, `amulet-timing`, `compare`, `eval`, `experiments` (everything in order).

## SpecLFB split (proposal; needs Anna's sign-off)

**Finding: Anna's premise is partly right.** SpecLFB does involve stores, but only as a speculation source, and InvisiSpec-Futuristic and CleanupSpec involve them the same way. SpecLFB treats a load as unsafe after an unresolved branch (CUSL) or after an older store with an unresolved address (MUSL): SpecLFB paper §5 (PDF p6) "MUSLs in an Unresolved Memory Access Order ... the speculative loads causing cache misses that follow the stores are the MUSLs to be protected"; §6.2.1 (p7) instructions using the store queue are marked unsafe; §6.2.2 (p8) dependencies tracked through LDQ/STQ; the tested build implements `isUnsafe = (isCUSL() || isMUSL()) && isReallyUnsafe()` (AMuLeT p12-13, Fig. 8c). No paper makes a store a transmitter: SpecLFB protects "speculative loads causing cache misses" (§5), TLB/port contention out of scope (§4, p5), cache hits out of scope (§9, p13); InvisiSpec p4 "we limit ourselves to load instructions"; CleanupSpec covers the data cache only, RFOs issued non-speculatively (p8). The store source is not unique to SpecLFB: InvisiSpec-Futuristic (the mode AMuLeT and we run) covers loads "that can be squashed by an earlier instruction" (p4) and lists store-load aliasing (Table I, p3); CleanupSpec deems all transient instructions unsafe until retire (§2.1 p3) and lists SSB (§7 p12). So "SpecLFB uses stores, the other two only loads" holds only against InvisiSpec-Spectre.
