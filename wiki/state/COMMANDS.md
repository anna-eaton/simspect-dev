# COMMANDS — every `make` target (the command reference)

*Living doc. **Keep this in sync whenever a Makefile target or `scripts/sim` command changes** —
see the "Documentation is proactive" directive in the root `CLAUDE.md`.*

Variables (override on the command line): `MODEL` (Alloy stem), `CONFIG` (generation config),
`RUNCONFIG` (gem5 execution config), `FORCE=1` (re-run even if output exists), `PORT`, `W` (tmux
window for `peek`), `CMD` (command string for `launch`). Defaults: `MODEL=STT_6`,
`CONFIG=runconfigs/run_config_STT_6.jsonc`, `RUNCONFIG=$(CONFIG)`.

## Sessions / infra — connect-or-create the rig from anywhere
These wrap `scripts/sim` (config in `scripts/simspect.env`). Full runbook: [`INFRA.md`](INFRA.md).

## Low-level engine — single build, sequential (what the watchers use)
| command | what it does |
|---|---|
| `make all MODEL=… CONFIG=… [FORCE=1]` | `pipeline.py all` — phases xml→llvm→asm→gem5 in sequence. |
| `make xml` / `make llvm` / `make asm` / `make gem5` | Run one phase (`pipeline.py <phase>`). Idempotent/resumable; `FORCE=1` to regenerate. |
| `make clean MODEL=… CONFIG=…` | `pipeline.py clean` for that model/config. |

## Footprint checker (InvisiSpec / SpecLFB / CleanupSpec) — `check_footprint.py` + a criterion JSON
The footprint defenses are checked by ONE generic checker, `STAGE3_gem5/check_footprint.py`, which reads only the O3PipeView trace (normal records + the SimSpect hook lines, `wiki/design/SIMSPECT_HOOKS.md`) and a criterion `specs/leakage/{invisispec,speclfb,cleanupspec}.json` (schema and predicates: `wiki/design/TRANSMISSION_CRITERIA_FORMAT.md` "Criterion JSONs + checker"). It needs a hooked build (`amulet-*` after 2026-10-28); on a trace with no simspect lines it returns `status=warn`, `issued_in_window=null`.

| command / key | what it does |
|---|---|
| run_config `gem5.checker: "check_footprint.py"` + `gem5.criterion: "specs/leakage/<defense>.json"` | `pipeline.py gem5` (and `make run`/`testrun.py`, which call it) sends **every** test to that checker instead of the per-kind table (`_checker_for`); `criterion` becomes env `SIMSPECT_CRITERION`. Absent → unchanged kind-table behavior. |
| run_config `gem5.criterion_actor: "spec" \| "futuristic"` | Optional override of the actor mode (env `SIMSPECT_CRITERION_ACTOR`); default = the criterion's `actors.select_by_scheme` on the last `--scheme=<Name>` in `extra_args` (InvisiSpec: `FuturisticSafeInvisibleSpec` → `futuristic`). |
| `python3 STAGE3_gem5/check_footprint.py <dir> --criterion specs/leakage/<d>.json [--jobs N] [--scheme N] [--out r.json] [--actor M]` | Same CLI shape as `check_ld.py`; builds + runs gem5 via `gem5_common` (mirror the campaign's env as usual). Records carry `issued_in_window` (= `leak`), `terms_fired`, `offending` (struct, line, event ids), and for CleanupSpec `per_line` counts, `skip_drop`, `net_state`, `inconsistent`. |
| `python3 STAGE3_gem5/check_st.py <dir> [--jobs N] [--scheme N] [--out r.json]` | Store-transmitter checker (`xmit.kind == "str"`, routed automatically by `pipeline.py:_KIND_TO_CHECKER`): leak = LSQUnit "Executing store PC" tick inside check_ld's window (lc retired, before fnc, branches unresolved); no data-obtained gate. Built for SPT's store-address contract (SPT §7.4, p. 9); needs the `LSQUnit` debug flag (default). Validated 2026-11-16 on cafe2 `/tests/sptstore_20261116/run.sh` (claudelog). |
| `python3 STAGE3_gem5/check_footprint.py --trace pipeview.txt --meta meta.json --criterion <json> [--out r.json]` | Offline: evaluate an existing trace, no gem5 (meta = `lc_pc`, `fnc_pc`, `unresolved`, `ticks_per_cycle`, `cmd`). |
| `python3 STAGE3_gem5/tests/test_check_footprint.py` | Unit tests (synthetic traces) + regression on real hooked traces in `STAGE3_gem5/tests/fixtures/` (UV1 leak, UV6 leak, uv5clean no-leak, uv4split leak, InvisiSpec Futuristic). |

## Fast path (default since 2026-11-16)

**Default ON since 2026-11-16 (Anna: "just keep the fast path as our path now"; it gives verdict-identical records, 300/300 per defense).** A config without `gem5.fast_path` now runs the fast path in `pipeline.py`, `testrun.py` and `timing_driver.py`; set `"fast_path": false` to get the production path (e.g. for an equivalence check). The text below describes the mechanism as first added (opt-in).


**What it is.** A harness-only speed-up of each SimSpect test (TC-1, decided by Anna 2026-11-16; built by agent fastpath). It is **off by default**: with `gem5.fast_path` absent or `false`, every config, script and running campaign behaves exactly as before. Turned on, it changes only how the same inputs are read and in which process the same Python functions run: (1) the gem5 binary's resolve-hook scan (`gem5_common.binary_has_resolve_hooks`, a 0.6-1.1 GB read) is cached per binary (real path, size, mtime, inode) instead of being repeated in every fresh checker process; (2) inside each test the trace is read once and each parser gets only the lines its patterns can match, instead of eight full passes; (3) in the per-test drivers (`firstdet_stream.py`, `timing_driver.py`, TIME-1) each test's `pipeline.py gem5` command runs in a persistent Python worker instead of two fresh interpreters. Unchanged: the gem5 binary and command line (debug flags incl. Commit, cache setup, branch forces, stalls), one gem5 process per test (no batching, TC-2), every checker's decision code. Code: `STAGE3_gem5/gem5_fastpath.py` (1, 2), `STAGE3_gem5/timing/fastpath_worker.py` (3), `STAGE3_gem5/timing/fastpath_equiv.py` (equivalence check); the evidence is in `wiki/state/EVAL_MANIFEST.md` "Per-test cost and setup amortization (2026-11-16)".

**Where it acts.**

| entry point | what the key turns on | why |
|---|---|---|
| `firstdet_stream.py`, `timing_driver.py`, TIME-1 `run_simspect.sh` / `retime_fast.sh` | 1 + 2 + 3 | one `pipeline.py gem5` per test, so per-test interpreters and scans dominate |
| `pipeline.py gem5` / `all`, `testrun.py`, `results/_sweep_watcher.py`, shard launchers | 1 + 2 | they already run up to 1,000-2,000 tests per checker process, so only the trace read is per test |

All checkers are covered (`check_footprint`, `check_ld`, `check_br`, `check_other` and the `check_ld_*` variants), because the change sits in the shared parsers, not in any checker. A worker serves one checker script; a test whose checker differs gets a worker of its own.

**Prerequisite.** The fast-path files must be in the code tree you run from. Anna runs `make sync` on the Mac, then on the node: `cd <code root> && git pull` (cafe2's checkout is `/tests/simspect`). A campaign that runs from a copied code snapshot (e.g. `/tests/bigcorpus_20261115/code`) needs these files copied into it: `STAGE3_gem5/gem5_fastpath.py`, `STAGE3_gem5/gem5_common.py`, `pipeline.py`, `testrun.py`, `STAGE3_gem5/timing/{fastpath_worker,fastpath_equiv,timing_driver,firstdet_stream}.py`. Never edit the snapshot a live campaign is reading.

**Turn it on.** One key in the run config's `gem5` block, nothing else:

```diff
   "gem5": {
     "binary": "/work/amulet/amulet-gem5-CleanupSpec_AE-v1.1/build/X86_MESI_Two_Level/gem5.opt",
     ...
     "cache_setup": "random_all",
+    "fast_path": true,
     "extra_args": [ ... ]
   }
```

Only JSON `true` / `false` are accepted; anything else (e.g. the string `"true"`) stops `pipeline.py` and the drivers with an error. `pipeline._build_gem5_env` turns the key into `SIMSPECT_FAST_PATH=1` for the checker processes; without the key a stray `SIMSPECT_FAST_PATH` in your shell is dropped, so the config is the only switch.

**Check equivalence first (one command per config).** Run on a held node, inside `gem5_dev`, at nice 19, from the code root. It runs every test twice, production then fast path, and compares the full records:

```bash
cd <code root> && TMPDIR=/tmp nice -n 19 python3 STAGE3_gem5/timing/fastpath_equiv.py driver --code-root $PWD \
    --config <run_config.jsonc> --model <testset model> --out /tests/<fresh dir>/eq_<row> --sample 300 --parallel 8 \
    [--pairs-file <tsv: mode<TAB>stem of known hits>]
```

How to read it: the last log line is `END driver: N/N identical, 0 different, harness errors 0; ...`, and the exit status is 0. Anything else fails: each differing test gets `diffs/<mode>__<stem>.json` (field path, production value, fast value), and `equiv_report.json` holds per-test CPU-s for both paths (`cpu_mean`, `cpu_ratio`, `per_cache_setup`). It compares, per test, the checker record(s) key by key (minus the temp `workdir` path), the aggregated `window-results.json` record, the sweep sidecar (stall points) and the `results.jsonl` row minus timing fields. Random temp-directory names (tempfile's 8-character suffixes) are masked in strings, since they differ between any two runs. Optional extra checks: `batch` (the `pipeline.py gem5` / `testrun.py` path, one call per side with `--jobs 8`); `errcases` (builds a synthetic error testset: assembler failure, `.ann.json` without `xmit.kind`, without the transmitter address, an unmapped load that makes gem5 panic; then run `driver` on it); `driver` with `SIMSPECT_GEM5_TIMEOUT_S=0` in the env (every gem5 times out); `--ab prod,prod` (A/A determinism control); `stored --run <eq dir> --stored <an earlier campaign of the same config>` (the default path equals what the old code wrote); `parsers --traces '<glob of *.pipeview.txt.gz>'` (offline, no gem5). The exact campaign run on 2026-11-16 is `STAGE3_gem5/timing/fastpath_equiv_run_20261116.sh`.

**Re-time per-test CPU (TC-4).** Use an idle node (no other campaign; TIME-1 used cafe2) that holds `/tests/timing_20261115` (TIME-1's configs, 1,000-pair sample and testset). From the Mac, after `make sync` and a pull on the node:

```bash
ssh -A cafe2 "docker exec -it gem5_dev tmux new -A -s retime"     # then, inside:
cd /tests/simspect && CODE=/tests/simspect bash STAGE3_gem5/timing/time1_20261115/retime_fast.sh "T1g T2g T3g" 16
```

Per row it runs TIME-1's harness twice, back to back and pinned exactly like TIME-1 (`taskset -c 0-31`, 16 workers, `firstdet_stream.py`, the TIME-1 sample and config): first production (`simspect/<row>_p16_prod2/`), then the same config plus `"fast_path": true` (`simspect/<row>_p16_fast/`, config `configs/<row>_time1_fast.jsonc`). It finishes with `retime_fast_summary.py`, which writes `/tests/timing_20261115/retime_fast/summary.{md,json}`: CPU-s per test for TIME-1 / production rerun / fast path, the speedup, per cache setup and gem5-only CPU, and a check that every fast row equals the rerun row and every hit's raw record is identical (exit 1 otherwise). Rows where the rerun differs from TIME-1 itself are counted separately: that is code or node drift since 2026-11-15, not the fast path. About 1 h for all three rows. Log: `/tests/timing_20261115/retime_fast/retime.log`.

**Logs and per-test path.** Drivers: `driver.log` says `fastpath: ON` at start and gives each test's path. `results.jsonl` rows carry `exec_path` (`fast`; `fast_partial` if a checker batch had to run as a subprocess; `production` if the worker failed and the test was rerun the production way, with `fastpath_fallback` = why). Worker logs go to `<out>/fastpath_logs/worker_<n>_<checker>.log` (start, bind, every test with rc / CPU / path, the per-test trace-read line, every error with traceback). Spawn and exit records, including each worker's one-time startup CPU, go to `<out>/fastpath_workers.jsonl`. Batch path: `fastpath.log` next to the batch outputs (`pipeline.py`: the results mode dir or `sweep/raw_results/`; `testrun.py`: `<campaign>/<mode>/fastpath.log`), one line per test (path fast or production and why, trace size, lines per class). A trace larger than 512 MB (`SIMSPECT_FAST_PATH_MAX_TRACE_MB`) or one whose single read fails is parsed the production way and logged.

**Fall back.** Set `"fast_path": false` (or delete the key) and rerun. Nothing else changes: same outputs and file layout, and the records are identical. A resumed campaign can switch either way, but then its `total_cpu_s` column mixes two harnesses, so don't compute CPU per detection over such a campaign (DECIDE TC-5).

## FP-register routing as an alternative (fpr.p) — 2026-11-16

Anna (2026-11-16): routing every consumed load through an xmm register (recipe A: `fpr` without `p`, so no test of the evaluated corpora is integer-only) is bad practice; vector-register routing is an alternative concretization of a load, next to the integer one. `parsexml.py` `pass5_emit_llvm` takes an optional `fpr.p`: each eligible load is routed with probability `p`, decided by its own rng seeded `fpr_p:<stem>`, and a load that is not routed is emitted exactly as with `fpr` off. Absent = byte-identical to before (verified on 40 corpus tests and the 32 unit-test fixtures); `p = 0` gives the same `.ll` as `fpr` off; `p = 1` the same `.ll` as absent. When `p` is set, `.ann.json` `fpr` also has `p` and `n_eligible`. Note: the interleave-only filler category (recipe A) has SSE entries on scratch xmm14/xmm15 whose outputs are never read, so a test with no routed load can still contain xmm14/xmm15. Pristine reference copy: `STAGE2_compilation/proposed/pre_fpr_p_20261116/parsexml.py`.
