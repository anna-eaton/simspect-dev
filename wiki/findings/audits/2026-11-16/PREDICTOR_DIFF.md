# Branch-predictor audit of every reported gem5 build (2026-11-16)

**Question (ISCA-27 Discussion \reviewnote):** does any of the gem5 builds we report change `src/cpu/pred/` beyond our hooks? The paper says: "No defense we test changes how the predictor predicts (STT delays only its updates [STT §6.4.1]), so forcing a prediction changes only which path the core speculates down, not how the defense handles it."

**Answer: the sentence holds for every build.** In no build does any change other than our hooks alter how a prediction is made (the lookup that returns direction and target). The defense authors' changes in `src/cpu/pred/` are (i) an unused `StaticBP` class (STT, SPT, AMuLeT's old trees), (ii) print-only `DPRINTF`s and a prediction log (AMuLeT), and (iii) checkpoint and reset code for the Tournament predictor that only AMuLeT's own harness calls. Outside `src/cpu/pred/`, the one change to predictor behavior is STT's delayed squash-time update (`src/cpu/o3/fetch_impl.hh:1004-1070`), which the paper already cites; SPT carries the same code but only in its Eager mode, which our SPT row does not use. Two facts the paper does not mention but which don't contradict it: **SPT's authors changed the default predictor from Tournament to LTAGE** (`src/cpu/o3/O3CPU.py:161-166`), and our AMuLeT-parity rows select `--bp-type=BiModeBP`. Both are upstream predictors used unchanged. Recommendation: the \reviewnote can be removed; whether to add a half-sentence about SPT's LTAGE default is Anna's call (DECIDE PRED-1 below).

Method: read-only on every tree. Each build's `src/cpu/pred/` was hashed blob by blob (`git hash-object`) and matched against every historical state of upstream `src/cpu/pred/` in a blobless clone of `https://github.com/gem5/gem5` (`~/trippel/gem5-upstream.git`). The authors' pristine trees came from git `HEAD` (`/work/stt`, `/work/gem5-spt`), from `/work/gem5-recon` (the authors' ReCon tree, identical to `~/Downloads/dockerrecon/gem5-recon`), and from the AE tags of `https://github.com/sith-lab/amulet-gem5` (`~/trippel/amulet-gem5-upstream.git`; the `~/trippel/defense_src/amulet-*` copies are NOT pristine, they already hold our branch-force hook). Diff chain per build: upstream → authors' tree → our hooked tree. Predictor call sites in `src/cpu/o3/` (`branchPred->…`, `BranchPredictor(...)` defaults) were compared the same way. Scripts: `scripts/predictor_diff_20261116/{match_upstream,file_lookup}.py`. Every diff and the hash table: `wiki/findings/audits/2026-11-16/predictor_diff_data/`. The `src/cpu/pred/` contents are identical (md5 of the directory) on cafe1, cafe2 and cafe3 for every tree present on each node (SPT is only on cafe2); `gem5-recon-ruby3` and `gem5-recon-modded-stl` are blob-identical to `gem5-recon-modded`, and `stt-master` (5bf4110) is blob-identical to `stt` (e3283b9).

## What our hook does (same in every build)

At the end of `BPredUnit::predict`, after the predictor has looked up direction and target and pushed its history, a PC found in `btbForcedTargets` gets its target overwritten (1 = fall through, i.e. predict not-taken; anything else = taken to that target) and `predict_record.predTaken` set to match; it prints a `BR:predict_force` line. For any PC not in the map nothing changes. The predictor's own history registers keep the direction it predicted, in every build alike. The resolve-stall table lives in the predictor object only as storage; IEW reads it.

## Contradictions with the paper's sentence

None. Two nuances Anna may want to know about, neither of which contradicts the sentence:

- SPT runs on LTAGE (the authors' default), the ReCon, STT and AMuLeT-eval rows on Tournament, and the AMuLeT-parity rows on BiMode. Forcing makes the predictor type irrelevant for the forced branches; it matters only for the unforced ones (committed and resolved branches).
- "STT delays only its updates": in the gem5 code the delayed part is the squash-time correction (history repair + training with the actual outcome, `BPredUnit::squash(seq, pc, taken, tid)`); the commit-time `update()` is not delayed (`fetch_impl.hh:1044-1048`). That matches the STT paper's description.
